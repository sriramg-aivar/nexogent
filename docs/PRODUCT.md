# Nexogent — Product Overview

## What it is
Nexogent is an **AWS SecOps agent that you deploy into a client's own AWS account**.
Once installed, it runs 24/7 inside the client's Amazon EKS cluster, continuously
giving the client a clear picture of their cloud security posture.

It is a **per-client product, not a SaaS**. Each client gets their own private
deployment inside their own account. Their data never leaves their account.

## What it does
1. **Discovers every AWS resource** across **all enabled regions** and groups them
   by service (EC2, S3, IAM, Lambda, RDS, DynamoDB, EKS, CloudTrail, …).
2. **Runs read-only security checks** — its own built-in checks plus the open-source
   **Prowler** scanner (hundreds of checks mapped to CIS / AWS FSBP). Additional
   open-source scanners (ScoutSuite, cloudsplaining) can be enabled per client,
   all normalized behind one finding model.
3. **Ranks every finding by real risk**, not just raw severity, using a scoring
   rubric (severity + exposure + reachability + resource criticality).
4. **Explains each finding in plain English** with concrete remediation steps,
   generated by **Amazon Bedrock** (with an offline fallback so it always works).
5. **Presents everything in a portal** (see below) where the client picks a service,
   then a resource, and sees what exists, what's misconfigured, and how to fix it.

## The client portal (v1)
After deployment the client opens the portal and signs in as **superadmin**
(superadmin = the client; v1 has this single role). The experience is:

1. **Sign in** — a login gate protects the portal so findings aren't public.
2. **Services landing** — all supported AWS services shown as cards, each with its
   resource count and finding count.
3. **Service page** — click a service to list all its resources, each tagged with
   its **region**, and a **region filter** to narrow the list.
4. **Resource page (the security/audit page)** — click a resource to see its
   findings, risk scores, and plain-English explanation + remediation.
5. **Audit on demand** — an **Audit** button on the service and resource pages runs
   the scanners (Prowler + built-in checks) for that target and returns fresh
   findings. Scheduled background scans keep the posture current between clicks.
6. **Enable these auditings** — GuardDuty, Security Hub, and Inspector appear as
   toggles for a future version; they are **disabled in v1** and not connected.

## What it does NOT do
- It is **read-only and recommend-only**. It never changes, deletes, restarts, or
  remediates anything in the account. Every output is a recommendation a human reviews.
- It is not a shared multi-tenant service. One deployment = one client account.
- It does not retain access after handover. The client holds full admin.

## Who it's for
Companies that want continuous, automated security coverage of their AWS account
without building a security team or standing up a heavy enterprise platform. They
hand us scoped deploy access, we install Nexogent into their account, and from then
on their dashboard shows their live posture.

## How a client engagement works
1. We share **PREREQUISITES.md** — the exact AWS access and resources needed.
2. The client provisions that access (temporary deploy credentials / role).
3. We deploy Nexogent into their EKS cluster via the Helm chart.
4. The agent runs; the client uses the portal as superadmin.
5. We hand over. The account and its admin remain entirely the client's.

## Technology
- **Pure Go** agent — a single small static binary, ideal for running inside a
  client's cluster with no interpreter or dependency sprawl.
- **Amazon Bedrock** (Claude) for the AI explanation/report layer — a hosted API,
  so there is no local ML model to train or run.
- **Open-source scanners** — Prowler (default), with ScoutSuite and cloudsplaining
  available to enable per client.
- **React** portal (Vite + Nginx), served behind an Application Load Balancer.
- **DynamoDB** stores review history so reports survive restarts and multiple replicas.
- **Helm** for repeatable per-client deployment onto Amazon EKS, with access via
  IAM Roles for Service Accounts (IRSA) — no static keys in the cluster.

## Why Go (and no Python)
A security product that lives inside someone else's account should be small,
auditable, and dependency-light. Go compiles to one static binary in a tiny
container. The "intelligence" is Amazon Bedrock, which Go calls directly over the
AWS SDK — so there is no need for a Python ML runtime anywhere in the product.
(The open-source scanners run as isolated Kubernetes Jobs; the agent itself stays
pure Go.)

## Positioning (honest)
Nexogent does **not** reinvent vulnerability detection. Detection is delegated to
native read-only AWS APIs and open-source scanners (Prowler, and optionally
ScoutSuite / cloudsplaining). Nexogent's value is the layer on top: **multi-region
resource inventory grouped by service, a per-resource security view, risk ranking,
plain-English explanations, a clean superadmin portal, on-demand + scheduled audits,
and one-command per-client deployment** — delivered safely as read-only, inside the
client's own account.
